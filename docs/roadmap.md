# Hycel roadmap to 1.0

This roadmap describes the path from the current kernel to a stable first release. It is outcome- and gate-based, not date-based: phases finish when their exit criteria are met, not when a calendar estimate expires. Subphases may overlap only when their dependencies are satisfied. Revisit scope after each phase; do not add features that threaten the 1.0 reliability bar.

## 1.0 destination

Hycel 1.0 will let a developer create, edit, build, run, test, and ship a small 2D desktop game on macOS, Linux, and Windows on x86-64 and ARM64. Its project data and core commands will be understandable to a person or AI agent, and its simulation will be inspectable and replayable. A small sample game will prove the complete workflow.

This does **not** promise a general-purpose 3D engine, consoles/mobile, multiplayer framework, visual scripting, or feature parity with mature commercial engines. 1.0 stability means documented and tested formats/APIs with explicit compatibility policy—not a claim that every imaginable game is supported.

## Phase overview

1. **Project foundation and product contract** — settle scope, support matrix, engineering rules, and decision gates.
2. **Deterministic simulation kernel** — grow the current clock into a tested, headless simulation runtime.
3. **Project, scene, and asset model** — define versioned, readable game data and validation/migration behavior.
4. **Cross-platform 2D runtime** — deliver the window, input, renderer, and first interactive scene across target systems.
5. **Core 2D game capabilities** — provide only the gameplay systems needed for a small complete game.
6. **Agent-native interface** — make human and agent workflows use the same stable, testable application services.
7. **Editor and content workflow** — add a useful visual authoring layer without making it the source of truth.
8. **Complete sample game and user experience** — prove Hycel by building and shipping a real small game with it.
9. **Hardening, compatibility, and release candidate** — test failure modes, compatibility, performance, packaging, and usability.
10. **1.0 release and maintenance readiness** — freeze contracts, publish artifacts, and establish the support process.

## Phase 1 — Project foundation and product contract

**Outcome:** Hycel's first-release boundaries are explicit, and the repository can safely grow without premature commitments.

### Subphases

1. **1.1 — Confirm product scope — COMPLETE.** Hycel is Rust-first, 2D, and desktop-focused. 1.0 explicitly promises small single-player side-view platformers at the scale defined in [`product-scope.md`](product-scope.md); general-purpose 3D and networking are out of scope.
2. **1.2 — Make the support matrix executable — COMPLETE.** Exact OS/architecture pairs, minimum OS floors, Rust MSRV/stable policy, and planned native graphics backends are recorded in [`support-matrix.md`](support-matrix.md). Its six native target rows drive CI. The revised MSRV 1.87.0 and six-row matrix passed native quality jobs, MSRV, docs, dependency audit, and renderer-probe builds in [CI run 36815524964](https://github.com/aaf2tbz/hycel/actions/runs/36815524964). Engine/runtime targets remain experimental until minimum-OS and packaging tests pass.
3. **1.3 — Establish engineering contracts — COMPLETE.** [`engineering-contracts.md`](engineering-contracts.md) and linked contributor/security guidance define crate boundaries, workspace unsafe-code prohibition, dependency review/audit, error policy, transactional data safety, local-first privacy, and no telemetry by default. The MSRV is 1.87.0 by explicit user decision to evaluate current wgpu 30 without the unmaintained transitive Metal dependency found in wgpu 26.
4. **1.4 — Set repository hygiene — COMPLETE.** Added issue forms, pull-request template, code of conduct, Keep a Changelog file/release categories, ownership and triage rules, CODEOWNERS, and CI-generated Cargo metadata/license inventory with pinned cargo-deny checks.
5. **1.5 — Run feasibility spikes — COMPLETE.** An isolated wgpu 30.0.1 + winit 0.30.13 probe builds on all six native OS/architecture rows. Runtime clear/present smoke passed on hosted macOS ARM64 (Metal, 99 frames), Linux x86-64 (llvmpipe/Vulkan, 5,181 frames), and Windows x86-64 (Microsoft Basic Render Driver/D3D12, 176 frames); local Apple M4/Metal also passed. Software adapters are CI feasibility only, not an end-user fallback promise.
6. **1.6 — Measure an initial clean build — COMPLETE.** The contributor setup passed on a fresh Ubuntu 24.04 hosted runner. [CI run 36815524964](https://github.com/aaf2tbz/hycel/actions/runs/36815524964) measured Rust 1.87.0 build/test at 0.21/0.25 seconds, stable 1.98.1 build/test at 0.59/0.17 seconds, and demo run at 0.15 seconds. Details and artifact reference are in [`development-baseline.md`](development-baseline.md).

**Exit gate:** Product scope, declared support matrix, security/data principles, and renderer/platform decision are written down. All accepted CI runner labels work in a test workflow. No major technical unknown blocks the 2D vertical slice.

## Phase 2 — Deterministic simulation kernel

**Outcome:** Game logic runs without a window, at explicit fixed ticks, and can be tested independently of the host OS.

### Subphases

1. **2.1 — Specify time and catch-up policy — COMPLETE.** `hycel-core::FixedClock` uses a 60 Hz initial default and host-supplied integer nanoseconds; `TimeScale` uses deterministic Q32.32 ratios, including zero-scale pause; interactive advancement is explicitly capped (default eight steps), reports dropped whole wall-time debt, preserves the fractional remainder, and never skips logical tick IDs. Tests cover rate, drift, pause, slow motion, catch-up, and failure atomicity.
2. **2.2 — Establish world primitives — COMPLETE.** Added generation-checked `EntityId` allocation/reuse, live-entity iteration, typed deterministic `ComponentStorage<T>`, explicit despawn/stale-component cleanup rules, fixed-point `SimScalar`, `Vec2`, `Angle`, and `Transform2D` in `hycel-core`. The APIs are documented in source and [`architecture.md`](architecture.md); tests cover reuse, stale handles, deterministic iteration, cleanup, math conventions, and arithmetic failures.
3. **2.3 — Build the deterministic schedule — COMPLETE.** `hycel-core::Schedule<State, Event>` freezes a serial `(order, SystemId)` system order before tick zero, consumes tick-matched ordered `InputFrame`s, derives independent PCG-XSH-RR 64/32 RNG streams from the seed/base stream/system ID, and delivers events next tick in canonical order. Tick errors restore cloned state, RNG, and pending events; callbacks are contractually forbidden from external side effects. The platformer demo now runs through this schedule.
4. **2.4 — Add replay and state inspection — COMPLETE.** `Replay` stores strict, bounded schema-1 JSON with engine/target/tick-rate/seed/stream metadata and contiguous input frames; playback validates compatibility and runs headlessly through the same schedule. `CanonicalState` supplies a versioned SHA-256 encoder with deterministic world/component/math implementations. The demo records, serializes, reloads, replays, and asserts a matching state hash; same-target determinism is covered, with no cross-architecture guarantee claimed. Dependency and format decisions are in [`ADR 0002`](adr/0002-replay-format-and-state-hash.md). All six native target jobs, including the replay/hash test suite, passed in [CI run 36875349085](https://github.com/aaf2tbz/hycel/actions/runs/36875349085).
5. **2.5 — Specify concurrency boundaries — COMPLETE.** The authoritative simulation schedule is serial and single-threaded; callbacks have isolated deterministic RNG and next-tick event interfaces. Worker threads may prepare immutable presentation/build/asset results, but may not mutate authoritative state or affect simulation ordering. Parallel simulation requires an explicit deterministic conflict/merge/failure model and cross-platform replay/hash evidence; see [`architecture.md`](architecture.md).
6. **2.6 — Add invariants and regression tests — COMPLETE.** Tests cover pause/resume, bounded catch-up, stable IDs, deterministic system/event ordering, replay/hash equality, tick failure rollback, and explicit clock/schedule tick-overflow atomicity. Workspace tests and Clippy, MSRV tests, docs, dependency audits, and all six native targets passed in [CI run 36877007899](https://github.com/aaf2tbz/hycel/actions/runs/36877007899).

**Exit gate:** Headless sample simulation can run, stop, replay, and report state with no window/GPU dependency. Repeated runs produce the same state hash on supported test targets; any cross-architecture guarantee is stated only if demonstrated.

## Phase 3 — Project, scene, and asset model

**Outcome:** A Hycel project is readable, versioned, validated, diffable, and safe to migrate.

### Subphases

1. **3.1 — Define project layout and manifest — COMPLETE.** [`project-format.md`](project-format.md) specifies the TOML manifest and JSON scene/resource contract, stable project identity, inclusive/exclusive engine SemVer compatibility range, fixed `src/`, `assets/`, and `scenes/` content roots, build profiles, generated directories, and path-boundary rules. A representative manifest is in [`examples/empty-project`](../examples/empty-project/hycel.toml).
2. **3.2 — Define scene/resource schemas — COMPLETE.** [`scene-format.md`](scene-format.md) defines bounded UTF-8 JSON scene/resource schema 1, canonical UUID identities distinct from runtime handles, parent/component/resource references, fixed-point transform defaults, authored ordering, and reject-unknown behavior. A sample scene is in [`examples/empty-project/scenes`](../examples/empty-project/scenes/first-room.json). Keep serialization separate from runtime implementation details.
3. **3.3 — Implement strict validation — COMPLETE.** New `hycel-project` APIs bound TOML/JSON parsing, reject unknown/duplicate fields, validate manifest profiles and SemVer ranges, scene UUIDs/transforms/parents/cycles/component/resource registries, project-wide IDs and declared entity/resource references, project layout, and project-relative paths including canonical symlink escapes. Diagnostics use stable `HYCEL-*` codes and retain file/path context. All six native targets, MSRV, dependency audit, docs, and renderer checks passed in [CI run 36901782297](https://github.com/aaf2tbz/hycel/actions/runs/36901782297).
4. **3.4 — Implement transactional migration — COMPLETE.** Scene schema 2 adds strict entity tags; schema 1 migrates by adding empty arrays. The project crate has validated in-memory conversion, per-file atomic migration, numbered non-overwriting backups, and validated rollback. Tests cover field preservation, injected interruption, concurrent edits, read-only/symlink rejection, backup collisions, and rollback. `project-format.md` records migration support and fail-closed policy for every persisted format. All six native targets, MSRV, dependency audit, docs, and renderer checks passed in [CI run 36924225517](https://github.com/aaf2tbz/hycel/actions/runs/36924225517).
5. **3.5 — Establish asset identity and dependency tracking — COMPLETE.** `hycel-assets` streams bounded project-relative sources into SHA-256 content IDs, snapshots strict import records/settings/tool versions, computes versioned fingerprints, gives hybrid UUID/fingerprint cache paths, reports direct scene/resource dependencies, and decides whether to reuse/reimport without timestamps. The design and deterministic-input contract are in [`asset-pipeline.md`](asset-pipeline.md). Format decoding, automatic descriptor discovery, and transactional importer execution remain future work. All six native target jobs, MSRV, dependency audit, docs/hygiene, and renderer checks passed in [CI run 36937119291](https://github.com/aaf2tbz/hycel/actions/runs/36937119291).
6. **3.6 — Add project CLI foundations — COMPLETE.** `hycel-cli` provides `new`, `check`, and read-only `inspect`, versioned JSON output, stable exit codes, and deterministic, bounded project discovery. `ProjectManifest` can be created and round-tripped through TOML; new projects are validated before success is reported. Tests cover command round-trips, errors, no-overwrite behavior, oversized/invalid documents, symlink escapes, and aggregate byte limits. Command schemas, filesystem behavior, dependency review, and the current empty-registry limitation are documented in [`cli.md`](cli.md). All six native targets, Rust 1.87 MSRV, dependency audit, docs/hygiene, and renderer checks passed in [CI run 36940832274](https://github.com/aaf2tbz/hycel/actions/runs/36940832274).

**Exit gate:** A clean project can be created, parsed, validated, inspected, migrated between at least two schema versions, and round-tripped without unintentional data loss. Invalid fixtures produce actionable diagnostics.

## Phase 4 — Cross-platform 2D runtime

**Outcome:** A cross-platform 2D runtime implementation builds/tests on all six planned target pairs and opens/renders a simple scene on representative native runners. Full per-device certification is deferred to later release hardening; this phase does not certify target support.

### Subphases

1. **4.1 — Finalize platform/rendering ADR — COMPLETE (provisional).** [`ADR 0001`](adr/0001-windowing-and-renderer.md) provisionally selects wgpu 30.0.1 + winit 0.31.0-beta.3 + pollster 1.0.1 for Phase 4 implementation behind Hycel-owned interfaces. The beta probe passes formatting, tests, Clippy, dependency audit, MSRV tests, and native builds on all six CI targets; hosted Linux/Vulkan, macOS/Metal, and Windows/D3D12 clear/present smokes also passed in [CI run 36945427870](https://github.com/aaf2tbz/hycel/actions/runs/36945427870), with a local Apple M4/Metal smoke. Stable winit 0.31 adoption and physical Windows mixed-DPI validation are deferred target-certification work before any corresponding support claim; issue #4721 and packaging/minimum-OS evidence are tracked.

Unit tests cover config, event normalization, close/exit behavior, raw-handle trait bounds, and error source preservation. CI run 36948024650 passed the six native target jobs, Rust 1.87 MSRV, dependency/docs checks, and native window/redraw smokes on Linux x86-64, macOS ARM64, and Windows x86-64. Native resize/focus event observation varied by runner; the smoke is not physical input automation or mixed-DPI validation.
3. **4.3 — Implement a minimal render path — COMPLETE (initial path).** `hycel-render` creates a native wgpu surface/device, selects an sRGB-capable format, clears and draws a colored quad plus a generated nearest-filtered textured quad, applies 2D camera/viewport transforms, handles zero-size/outdated/lost surfaces, and reports shader/device failures through typed errors. 4. **4.4 — Add 2D presentation basics — COMPLETE.** `hycel-render` accepts bounded decoded RGBA images, assigns renderer-local texture IDs, draws camera-projected sprites in stable layer/order with linear RGBA tint/alpha, and draws a bounded physical-pixel 5x7 bitmap text overlay. 5. **4.5 — Normalize input — COMPLETE.** New `hycel-input` provides strict version-1 `input.json` bindings, supported stable physical key/mouse-button types, and deterministic digital-button/axis mapping to tick-indexed `InputFrame`s. `hycel-platform` normalizes its supported winit physical key/button subset; `hycel-project` validates optional input files; `hycel new` writes a starter map. Full-workspace stable/MSRV tests and release build, docs/dependency audit, six-target compile checks, local 30-frame window smoke, all six native quality/build jobs, and Linux x86-64/macOS ARM64/Windows x86-64 hosted presentation smokes passed in [CI run 36960784948](https://github.com/Clockroot/hycel/actions/runs/36960784948). **Exit gate:** The runtime implementation builds/tests on all six planned targets, representative native window/render smokes pass, and limitations/build instructions are documented. Device-, minimum-OS-, and packaged-game certification remains a later release gate before any target is called supported.

## Phase 5 — Core 2D game capabilities

**Outcome:** The engine supports the mechanics and content needed for the chosen sample game without ballooning into a general engine feature checklist.

### Subphases

1. **5.1 — Choose the gameplay capability set — COMPLETE.** The reference game is a short single-player side-view platformer with collision, hazards/objective, retry/checkpoint/transition, and completion flow. Per user decision, its required scope also includes basic audio and persistent local stage/checkpoint progress. `product-scope.md` is updated, and [`gameplay-scope.md`](gameplay-scope.md) records boundaries: no cloud/multiplayer saves, advanced audio, or general-purpose physics/audio tools. Backend and save-format choices remain for their implementation subphases.
2. **5.2 — Add collision and physics — COMPLETE.** Per user decision, `hycel-physics` wraps Rapier2D 0.32.0 behind Hycel-owned box/body/state/contact types, uses `enhanced-determinism` without SIMD/parallel features, steps only contiguous explicit ticks, bounds body/coordinate inputs, and orders contact transitions by stable Hycel body IDs. Tests cover clone parity, simultaneous contacts, CCD tunneling prevention, contact removal, invalid geometry/ranges, and tick sequencing. Full workspace stable/MSRV tests, strict Clippy, native release builds, docs, dependency audit, and hosted six-target native CI passed in [CI run 36964450531](https://github.com/Clockroot/hycel/actions/runs/36964450531). Cross-platform replay identity and physical hardware support are not claimed.
3. **5.3 — Add game input actions and events — COMPLETE.** Schema 2 names actions while retaining explicit stable IDs used by input frames/replays; strict schema-1 documents migrate in memory without changing IDs. Action names resolve to IDs through `InputBindings::action_id`; press/release edges derive from contiguous tick frames through `ActionEventTracker`, so recorded and replayed input yields identical events. Native events remain outside gameplay APIs. Stable/MSRV workspace tests, strict Clippy, docs, dependency audit, release builds, and hosted six-target native CI passed in [CI run 36966964253](https://github.com/Clockroot/hycel/actions/runs/36966964253).
4. **5.4 — Add animation and scene transitions — COMPLETE.** `hycel-project` parses bounded strict schema-1 animation clips using stable texture-resource UUIDs and positive tick durations. Scene schema uses `hycel.animation` with a clip resource UUID; the CLI validates clip source documents, dangling/wrong-kind references, and reports scene→animation and animation→texture edges in `inspect`. New `hycel-animation` advances authored clips on contiguous explicit ticks with deterministic completion/wrap events and applies validated scene transitions only on the following tick. The empty-project example and authoring docs exercise these contracts. Stable/MSRV workspace tests and release builds, strict Clippy, docs, dependency audit, and hosted six-target native CI passed in [CI run 36969842809](https://github.com/Clockroot/hycel/actions/runs/36969842809).
5. **5.5 — Add audio if required by the sample — COMPLETE.** Per user decision, Kira is behind `hycel-audio`; bounded (64 MiB) in-memory clips support WAV, FLAC, MP3, Ogg/Vorbis, and PCM, with one looping music voice, up to 32 effect voices, inspectable silent fallback, and a bounded diagnostic queue. The user approved narrowly scoped MPL-2.0 exceptions for Symphonia decoder crates and `triple_buffer`; see [ADR 0004](adr/0004-audio-backend.md). Stable/MSRV tests and release builds, strict Clippy, docs, dependency-policy checks, and hosted native CI for all six targets passed in [CI run 36974780399](https://github.com/Clockroot/hycel/actions/runs/36974780399). 6. **5.6 — Add save/load only if required — COMPLETE.** User selected per-user OS local data keyed by stable game UUID and one last-known-good backup with explicit recovery. New `hycel-save` stores only strict schema-1 scene/checkpoint progress, caps files at 1 MiB and completed scenes at 256, and atomically replaces primary/backup files. Bounded corrupt primary bytes are preserved before explicit recovery; oversized primaries remain untouched and require manual relocation, and unsupported future schemas are never downgraded. Full stable/MSRV workspace tests and release builds, strict Clippy, docs, dependency audit, and hosted six-target CI passed in [CI run 37092329728](https://github.com/Clockroot/hycel/actions/runs/37092329728); see [ADR 0005](adr/0005-progress-save.md).

Per user decision, the input figure is explicitly a CPU pipeline proxy, not input-to-photon latency. The native render smoke measures 100/1,000/5,000 sprite submissions/presentations, with its surface/display pacing limitations documented. Local Apple M4/Metal and CPU baselines plus one complete hosted adapter run are in [`performance-baselines.md`](performance-baselines.md). ## Phase 6 — Agent-native interface

**Outcome:** Agents at basic and advanced capability levels can reliably contribute changes and verify outcomes without privileged editor access.

### Subphases

1. **6.1 — Complete the file-native experience — COMPLETE.** [`agent-interface.md`](agent-interface.md) now has a concrete source-first quickstart, source/project/schema map, tick-driven code guidance, safe bounded Cargo validation commands, a realistic file-only starter task, and an explicit warning that the current CLI does not execute project code.
2. **6.2 — Stabilize CLI contracts — COMPLETE.** `run`, `test`, `replay`, `screenshot`, typed `edit` preview/apply, current-host `build`, and deterministic USTAR `package` have versioned JSON envelopes, stable diagnostics/exit behavior, and tests. `inspect` paginates scene/resource/dependency results; every CLI response has a 384 KiB cap and returns `HYCEL-CLI-199` rather than truncating. Native bundles run only the compiled-in reference game; authored `src/` is packaged as inert data. Bundle output is host-specific and experimental, not cross-target certification.
3. **6.3 — Add safe resource-level operations — PARTIAL.** CLI/project services expose read-only project/scene inspection and typed scene rename/transform/entity-tag replacement/entity-create/delete/registered-component-upsert/removal operations. Entity deletion refuses to orphan direct children; all results are strictly revalidated. Preview emits bounded diffs and source/candidate hashes; apply requires the exact source hash, validates again, makes a non-overwriting backup (rejecting pre-existing symlink/non-regular backup paths), preserves permissions, and atomically replaces the file. MCP additionally requires a single-use token bound to the previewed path/operation/hashes. Hash/path checks are not filesystem compare-and-swap against concurrent external changes. Typed empty-scene creation now has CLI/MCP preview/apply, whole-project validation, single-use MCP authorization, and non-overwriting publication; scene deletion remains open. Typed resource-descriptor source-path changes also have CLI/MCP preview/apply, hash-addressed backup restore, dependency revalidation, and regression coverage, while importer-setting edits and source-payload changes remain open until concrete importer setting schemas and value constraints exist; allowing arbitrary JSON here would imply validation guarantees the current import metadata layer does not provide. Exact scene-backup restoration is now a typed preview/apply operation (rather than a separate rollback command); external filesystem races remain outside its guarantee.
4. **6.4 — Add protocol adapters — COMPLETE (implemented subset).** `hycel-mcp` implements the MCP 2025-11-25 stdio lifecycle and bounded `tools/list`/`tools/call` subset over CLI/project services; it pins one root, is read-only by default, supports optional list/call fields and version fallback negotiation, returns JSON-RPC error IDs including null when unknown, and has unit/subprocess fixtures plus a pinned official TypeScript SDK 1.30.0 smoke that verifies read-only operations and the opt-in preview/apply/backup/single-use-token flow against a temporary project copy; its hosted Ubuntu CI job passed in run [37133176334](https://github.com/Clockroot/hycel/actions/runs/37133176334). Newer MCP revisions and full independent-client certification remain open.
5. **6.5 — Bound agent capabilities.** The adapter pins/canonicalizes the project root; rejects static traversal/symlink escapes; caps CLI output (384 KiB), MCP input/output (1 MiB), native bundles/packages (512 MiB), and project/replay/diff/screenshot work; performs no implicit network or project-code execution; and separates default read-only tools from startup-opt-in writes. Canonical path checks are not race-resistant against a concurrent filesystem mutator, and must not be treated as an OS security boundary. Explicit per-call deadlines and cancellation remain open.
6. **6.6 — Create agent conformance fixtures — COMPLETE (current interfaces).** A basic multi-step CLI task checks/inspects a project, runs a named test, previews/applies a scene edit, changes a resource source path and restores it from its exact hash-addressed backup, then asserts unrelated scenes/input/assets/notes are unchanged; it also previews/applies a bounded entity-tag change and verifies its backup. An advanced MCP subprocess task negotiates, inspects, previews/applies scene and resource changes with single-use tokens, restores the resource backup, checks backups and unrelated files, then validates; the MCP fixture also creates an entity, applies bounded tags through a second preview token, and deletes it. Other CLI/MCP tests cover replay, pagination, structured failures, bounds, root boundaries, USTAR packaging, non-overwrite behavior, safe archive extraction, and running the extracted bundle's named reference-game scenarios. These are deterministic fixtures, not an independent external-agent certification.
7. **6.7 — Test with independent agents — COMPLETE (bounded evidence; broader certification remains open).** Independent OpenAI Codex reviews (GPT-6-Luna and GPT-5.6-Sol) identified MCP compatibility and authorization defects against locally cached official SDK schemas; the implementation/tests/docs were revised for omitted `params`/`arguments`, `_meta`, version negotiation, error IDs, field bounds, preview-token binding, and request framing. A separate subprocess stdio fixture and a pinned official TypeScript MCP SDK 1.30.0 conformance script pass (`initialize`, `tools/list`, read-only tool exposure, inspection, project check, `echo-flight`, and opt-in temporary-copy preview/apply with backup/token-replay checks; negotiated revision `2025-11-25`); the script passed its hosted Ubuntu CI job in run [37133176334](https://github.com/Clockroot/hycel/actions/runs/37133176334). A local Qwen3:0.6b agent used a separate Python JSON-RPC stdio client to negotiate `2025-11-25`, list tools, validate the Courier project, and run `echo-flight`; it exposed that this advertised scenario was rejected by the MCP tool's allowlist. The allowlist now accepts it and a regression test verifies the MCP call. A local `qwen:latest` read-only review of the importer-inspection freshness correction completed without actionable findings. OpenCode-Go/GLM 5.2 and Qwen 3.7 review attempts failed with HTTP 403 because the required subscription was unavailable; a MiniMax M3 review attempt failed with HTTP 402 (insufficient balance). ## Phase 9 — Hardening, compatibility, and release candidate

**Outcome:** Common failures are caught before release, project data is protected, and compatibility promises are credible.

### Subphases

2. **9.2 — Fuzz and adversarially test parsers/importers.** Cover malformed/oversized files, path traversal, symlinks, decompression limits, interrupted I/O, invalid references, and corrupt resources. Fix panics and unbounded resource use.

## Cross-phase quality bar

These requirements apply throughout all phases, not just before 1.0:

- CI runs formatting, linting, tests, docs, dependency/ license checks, and native builds on every declared OS/architecture pair.
- No unsafe code in core unless a reviewed, documented exception is justified and isolated.
- Parsers and user data operations return typed errors; malformed user input must not crash the engine.
- Avoid silent data loss: explicit diffs, transactional writes, backups/migrations, and failure injection tests.
- Simulation determinism is carefully scoped and evidence-backed; never promise cross-platform bitwise identity by assumption.
- Agent-facing actions are documented, typed, bounded, least-privilege, observable, and tested with realistic tasks.
- No mandatory network service, account, cloud backend, or telemetry for core use.
- Third-party dependencies are reviewed for maintenance, security, license, platform coverage, and supply-chain risk.
